# Task List API

English | [繁體中文](README_TW.md)

A RESTful task list API written in Go on the standard library's `net/http` (no web framework), organised into middleware / controller / service / repository layers with constructor-based dependency injection.

## Requirements

- **Docker** — the image build brings its own Go toolchain, so nothing else needs to be installed; **or**
- **Go 1.27 or later**, since the code uses `net/http` method + path routing, `log/slog` and current dependency releases.

## Run

```bash
docker build -t taskapi .
docker run --rm -p 8080:8080 taskapi
```

### Without Docker

```bash
go run .
```

### Configuration

| Env var | Default | Meaning |
|---|---|---|
| `PORT` | `8080` | Listen port |
| `RATE_LIMIT_RPS` | `10` | Requests per second allowed per client IP |
| `RATE_LIMIT_BURST` | `20` | Maximum burst per client IP |

With Docker, pass them with `-e`, e.g. `docker run --rm -p 8080:8080 -e RATE_LIMIT_RPS=5 taskapi`. Invalid values stop the server at startup. Logs are JSON lines on stdout and include `trace_id` for request-scoped entries.

## Test

```bash
go test ./...                 # run all tests
go test -race -cover ./...    # with race detector (needs cgo) and coverage
```

Conventions: assertions use [testify](https://github.com/stretchr/testify) (`require` for preconditions, `assert` otherwise), test names follow `Test<Function>_<Case>_<Expected>`, and each test is split into Arrange / Act / Assert sections.

### Mocks

Service and controller tests use mocks generated by [mockgen](https://github.com/uber-go/mock) from the `TaskRepository` and `TaskService` interfaces (into `internal/repository/mocks` and `internal/service/mocks`). After changing an interface, regenerate them:

```bash
go generate ./...
```

mockgen is a `tool` dependency in `go.mod`, so `go generate` uses the pinned version and needs no separate install. Generated files are committed; do not edit them by hand.

## API

A task looks like `{"id": 1, "name": "Preview PR", "status": 0}`, where `status` is `0` (incomplete) or `1` (complete).

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/tasks` | – | `200` `{"result": [Task, ...]}` |
| POST | `/tasks` | `{"name": "...", "status": 0}` | `201` `{"result": Task}` |
| PUT | `/tasks/{id}` | `{"name": "...", "status": 1}` | `200` `{"result": Task}` |
| DELETE | `/tasks/{id}` | – | `204` (also when the task does not exist) |

Body rules: `name` is required, at most 100 characters; `status` is optional, `0` or `1`, defaulting to `0`. `PUT` replaces the whole task, so omitting `status` sets it back to `0`. Unknown fields are rejected and the body is limited to 1 MB.

`DELETE` is idempotent: it means "make sure this task does not exist", so it returns `204` even if the task was never created or was already deleted.

### Tracing

Every response carries an `X-Trace-Id` header. If the request sends an `X-Trace-Id` header, that value is reused so the request can be correlated with the caller's logs; otherwise a new 32-character hex id is generated.

### Errors

All errors use one format:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "request validation failed",
    "details": [
      { "field": "status", "reason": "oneof", "param": "0 1" }
    ],
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
  }
}
```

- `code` is stable and meant for programs; `message` is for humans and may change.
- `details` appears only for `VALIDATION_FAILED`; `reason` is the validator tag (`required`, `max`, `oneof`) and `param` its argument.
- `trace_id` matches the `X-Trace-Id` header, so it can be used to find the request in the logs.

| HTTP | `code` | When |
|---|---|---|
| 400 | `INVALID_JSON` | Malformed JSON, unknown field, wrong type, empty body, extra content after the JSON object |
| 400 | `VALIDATION_FAILED` | Body fails validation (see `details`) |
| 400 | `INVALID_ID` | `{id}` is not a positive integer |
| 404 | `TASK_NOT_FOUND` | `PUT` to a task id that does not exist (`DELETE` returns `204` instead) |
| 404 | `ROUTE_NOT_FOUND` | Unknown path |
| 405 | `METHOD_NOT_ALLOWED` | Wrong method for a path (an `Allow` header lists valid ones) |
| 413 | `PAYLOAD_TOO_LARGE` | Body over 1 MB |
| 429 | `RATE_LIMITED` | Too many requests from this IP (see `Retry-After` header) |
| 500 | `INTERNAL_ERROR` | Unexpected error; details are logged, never returned |

## Design

```
main.go                          read config, build DependencyProvider, run server with graceful shutdown
internal/
├── app/
│   ├── config.go                env-based configuration
│   ├── dependency_provider.go   the only place objects are constructed and wired (DI)
│   └── router.go                routes + middleware chain
├── middleware/                  trace id, per-IP rate limit, JSON 404/405 for unmatched routes
├── controller/                  decode + validate request, call service, write response
├── dto/                         API request shapes, their validate tags, validator setup
├── response/                    JSON / error writers, HTTP-only errors, error code → HTTP status
├── service/                     business logic, depends on repository.TaskRepository
├── repository/                  storage behind the TaskRepository interface (in-memory today)
├── model/                       Task, AppError and business errors (no HTTP knowledge)
└── trace/                       trace id helpers and a slog handler that adds trace_id
```

Request path: `[middleware: Trace → RateLimit → RouteErrors] → router → controller → service → repository`.

- **Routing**: standard library `http.ServeMux`, which supports method + path-parameter patterns such as `"PUT /tasks/{id}"` since Go 1.22, so no framework like gin is needed.
- **Dependency injection**: each `NewXxx` receives its dependencies as parameters and never constructs another layer itself; `app.NewDependencyProvider` builds everything bottom-up.
  - **Swapping storage**: moving to a database means writing a new `TaskRepository` and changing one line in the provider.
  - **Testing**: tests inject mocks directly (`service` tests use a mock repository, `controller` tests a mock service).
- **Validation vs. business rules**: format checks are validator tags on `dto.TaskRequest`, run by the controller. Business rules belong in the service. For example, the repository always reports a missing task as `TASK_NOT_FOUND`, and it is the service that decides this counts as success for `Delete` (idempotent) but is an error for `Update`.
- **Errors**: layers return `*model.AppError` values, which carry a code but no HTTP status. `response.WriteError` is the single place that turns them into JSON, using the code → status table in `response/errors.go`. Errors that only exist at the HTTP level (`INVALID_JSON`, `RATE_LIMITED`, ...) are defined in `response`, so `model`, `service` and `repository` know nothing about HTTP. Anything else becomes a 500 and is logged by the controller.
- **Rate limiting**: token bucket per client IP using `golang.org/x/time/rate`, with idle entries cleaned up every minute. State is in memory, so limits are per instance.
- **Concurrency**: `MemoryTaskRepository` guards its map with a `sync.RWMutex`; `TestCreate_ConcurrentCalls_StoresAllTasks` with `-race` checks this.
- **Graceful shutdown**: on SIGINT/SIGTERM the server stops accepting connections and waits up to 5 s for in-flight requests.
- **Docker**: multi-stage build produces a small Alpine image that runs as a non-root user.

### What I would add for production

- **Stateless scale-out**: move storage to a database (with pagination on `GET /tasks`) and rate-limit state to Redis, so multiple instances can run behind a load balancer.
- **Security**: authentication by validating JWTs from an identity provider, and authorization with role checks in middleware and ownership checks in the service layer.
- **Reliability**: `/health/live` and `/health/ready` endpoints so Kubernetes can tell whether an instance needs a restart and whether it can take traffic.
- **Observability**: ship stdout logs to Loki, expose Prometheus metrics, and add OpenTelemetry tracing, all correlated by trace id in Grafana with alerting.
- **CI/CD**: lint, `go test -race`, vulnerability and image scanning in CI; Helm for Kubernetes and Terraform for the rest of the infrastructure.
- **Testing and docs**: on top of the current unit tests (L0), add L1 tests that run against a real database in a dedicated container, and an OpenAPI spec.
